# 1.3.0 native row/gain controls and common-trigger timing

[Release notes](v1.3.0.md) · [中文更新说明](v1.3.0.zh-CN.md)

Use the current matched SDK/Agent 1.3.0 and Sensor Board 0.5.0 package.
Replace headers and every platform library together, even when the version
string remains 1.3.0. Core Runtime API 19, Network API 4 and Profile API 1
are unchanged; `camera_control_runtime_api.hpp` adds CameraControl API 1.
Windows consumers must resolve `prism_usb_sdk_get_camera_control_api` and
validate the table before using it. A missing extension is an error.

## 415M controls

`CameraRowGainConfig` provides per-camera manual integration rows and manual
gain. **Automatic exposure/gain switches, exposure/gain lower/upper bounds
and brightness target/deadband are all global**, shared by all four cameras.
The wire repeats these global fields in each record; unequal copies are
rejected by the SDK and Agent before any write. Use `cameraControlGlobals`
to read the shared settings and `withCameraControlGlobals` to expand a
`CameraControlGlobalSettings` into four configurations while preserving
per-camera manual values. Invalid bounds reject the whole request,
without silently clamping manual values. Rows are integers from 3 to 4096. Gain is an exact integer in
sixteenths: 16 means 1x and 900 means 56.25x. Brightness target/deadband use the
original RAW12 range, not the displayed thumbnail brightness. Firmware
capability and configuration validation remain authoritative.

- While idle, `cameraControlIdle()` reads desired settings in Agent RAM;
  `stageCameraControlIdle(current, config)` stages them using epoch/revision
  checks. Staging is neither a sensor readback nor persistent storage.
- While this client owns capture, call `beginCameraControlGet()` or
  `beginCameraControlSet(current, config)` and pass received frames through
  `finishCameraControl(frame, status)`. Keep consuming and acknowledging camera
  and IMU frames while the request is outstanding. No automatic STOP/START,
  transition-frame dropping or transition labels are required.
- Only one control request may be outstanding. `cameraControlPending()` also
  reports uncertain writes/replies. Do not blindly retry a timeout or malformed
  acknowledgement; a valid late response may still settle an outstanding call.
- `requested` is accepted configuration, not observed exposure. `observed`
  includes its own source-frame ID, rows, gain, revision and freshness flags;
  do not attach a status snapshot to an unrelated image or treat stale values
  as measured exposure. Shared trigger timing is not a direct LEDSTROBE pulse
  width measurement.
- RK-local exposes the same native controls and keeps its bounded receive
  queue active. Native controls, legacy live-row calls and recording switches
  exclude each other before changing pending state.

The original exposure/microsecond and live-row APIs remain available for
their compatible firmware, including 41M3. Do not use them as a fallback for
the new 415M native controller: matching firmware rejects obsolete control
paths instead of silently interpreting rows as microseconds.

## Timestamp and RAW12 semantics

Use the per-image timing mode after complete decoding and CRC validation:
mode 4 identifies the device's common external-trigger edge, mode 3 remains
an independent diagnostic event, and mode 0 means unknown time. Never make
independent timestamps equal in the viewer or assume device time is UTC.
Image pixels, source identity and timing metadata must stay associated.
Missing cameras do not justify renumbering or pairing frames from different
triggers. RAW12 decoding retains all twelve bits; thumbnail presentation
does not modify original recording data.

Builds and synthetic protocol tests are not new physical-device endurance or
cold-boot tests. Installing this SDK does not flash or operate hardware.
